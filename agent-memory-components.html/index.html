Agent 长期记忆：四层结构、离线整理，以及什么值得留下

研究范围：Anthropic《The components of agent memory》（2026-11-06，Lance Martin），以及 Claude Code memory、Managed Agents Dreams 文档。查证日期：2026-11-20。 证据状态：公开文章与文档阅读。后文分数、文件数和 Token 节省来自 Anthropic 的报告，本文没有复现实验。

上下文窗口解决的是当前会话能放下多少信息。长期记忆解决的是一次任务里得到的经验，如何在以后的会话里继续起作用。Anthropic 把空闲时的回放、纠错和整理叫做 Dreaming：主任务之外，用额外计算整理已经发生过的经验。整条链路是：新会话先注入少量记忆，执行中读取记忆并写下日志，Dreaming 再纠错、提炼、组织，最后更新长期记忆和索引。

四层可以记成一句话：Transcript 是原始经历，Memory Notes 是经验提炼，Memory Representations 是知识组织，Injected Context 是面向当前任务的精选入口。

给架构师的启发

先看该记什么。这部分给架构师的启发是：

  • 不要把所有事件都当作长期记忆。
  • 当前环境可以直接观察到的状态，未必值得重复保存。
  • 优先保存难以从环境重新获得的经验、规则、策略和用户偏好。
  • 记忆规模应服务于任务效果，而不是以文件数量或 Token 数量衡量。

Pokémon Red 把这四条摊开了。大约 10,000 步时，Sonnet 3.7 存了 413 个文件、225 个文件夹，大多是战斗、物品和 NPC 遭遇，进度是 1 枚徽章。金钱、当前位置每次都能从画面读到，反复保存没有太大价值，而且状态一直在变，记忆很快过期。它有一个阶段在 17 步里新建 6 个文件、删掉 9 个，游戏里没有采取任何行动。

Fable 5 只留了 9 个文件、2 个文件夹，加上顶层 global.md，进度是 4 枚徽章。global.md 记当前目标、下一步计划和记忆使用规则；其他目录记地点路线和打法。连续多次捕捉失败之后，它写下一条经过实践的规则：连续三次以上失败，就改变操作节奏，在菜单操作之间增加等待。这类规律画面不会直接给出，不写进记忆，新会话就丢了。

四层各自存什么

1. Transcripts：会话记录层

保存 Agent 执行任务时的原始交互：用户输入、模型响应、工具调用、工具结果和任务过程。

它的价值在于保留事实来源。后续发现某条记忆可能有误时，可以回到原始记录核对，而不是只能相信模型曾经写下的总结。Transcript 可以被搜索，也可以作为 Dreaming 的输入。

2. Memory Notes：经验笔记层

Agent 从一次或多次任务中提取值得保留的信息，写成相对简洁的记忆笔记。例如：

  • 用户明确要求后续始终使用某种输出格式；
  • 某个工具参数曾经导致任务失败，经过验证后发现正确用法；
  • 某项业务规则在多个任务中反复出现；
  • 某个问题的解决方法已经经过实际验证。

这一层的关键不是“把发生过的事情全部记录下来”，而是判断哪些信息在未来可能再次有用。写下一条记忆，就是在预测未来某个会话还会需要它。

这实际上是在测试 Agent 能否形成一个学习闭环：

回答问题 → 获得反馈 → 分析错误 → 验证原因 → 提炼规则 → 在后续任务中复用。

CL-Bench 1.0 的数据库问答就是这个闭环：每问在新会话里开始，但可以读上一问留下的记忆目录，答完后系统给出正确答案。较弱的模型可能只记下未经验证的猜测；更强的模型会把规则、证据来源、已确认事实和容易踩到的陷阱放在一起。Anthropic 报告的 mean reward：

模型无记忆使用记忆
Opus 5.50.6550.838
Sonnet 5.50.6440.833
Opus 50.5640.828
Opus 4.70.3830.700
Sonnet 50.3060.610
Sonnet 4.60.3300.364

记忆目录不会自动带来学习能力。Opus 5 是这一组里第一个把环闭合的模型；Opus 5.5 和 Sonnet 5.5 同样做到了。Sonnet 4.6 多停在未验证的猜测上，而且经常不读记忆；明确要求它先读、再检验假设之后，分数接近翻倍。

3. Memory Representations：记忆表示层

笔记不断增长之后，一堆独立笔记会越来越难理解和检索。Agent 可以进一步把笔记组织成更高层的知识表示，例如 Wiki：多个主题页面，页面之间用链接建立关系。

它的作用类似一张知识地图：

  • 主题页面聚合相关事实；
  • 页面链接连接跨主题的信息；
  • 索引帮助 Agent 快速定位；
  • 后续整理可以合并重复页面、修复错误链接和补充缺失内容。

这一层不是简单增加更多文本，而是把分散的记忆组织成更容易导航的结构。

4. Injected Context：注入上下文层

最重要、最常用的信息可以被提前加载到下一次会话的上下文中。

这样 Agent 不需要每次都先搜索记忆，便能直接获得关键背景、约束或当前目标。

但注入上下文必须严格控制规模：上下文 Token 有成本，错误记忆一旦被自动加载，也可能在每次会话中持续影响模型。加载进去也不等于会被遵守。Claude Code 的文档指出，更长的指令文件会降低遵循效果。

Dreaming 的五个作用

第一个作用：纠正错误记忆

记忆最大的风险之一是：错误信息可能被长期保留，并在未来被反复当成事实使用。

Agent 在任务中形成的判断，可能一开始就错，也可能因为环境变化而失效。Pokémon 的月见山任务里，模型曾错误记住宝可梦中心在山洞东侧。离开建筑后，它据此认为自己已经走出月见山，并把任务标成完成。实际上路线判断是错的，随后反复掉回原来的路径。Dreaming 的做法是回看原始 Session Transcript，把记忆笔记和实际行动核对，发现位置判断错误后修正对应记忆。修正之后，模型重新进入洞穴并到达华蓝市；保留错误记忆的那次多次陷入循环，没有完成目标。没有记忆的运行同样过不了这座山。

这里体现出一个重要架构原则：

记忆不能只负责写入，还必须能够被追溯、验证和修正。

如果系统只允许 Agent 不断追加记忆，却没有原始证据、冲突检测和纠错机制，那么长期运行后，记忆库可能逐渐积累错误。

第二个作用：把零散记忆组织成 Wiki

当记忆笔记变多，即使每条都准确，Agent 也不一定能高效找到它们。Anthropic 尝试让 Claude 在 Dreaming 阶段构建 Wiki：

  • 每个页面聚焦一个主题；
  • 页面之间建立关联链接；
  • 多轮整理逐步补充、修正和合并页面；
  • Agent 可以通过 Wiki 理解知识之间的关系，再结合搜索工具查找原始材料。

他们用大约 35 万份内部文档、约 4.2 亿 Token 的语料，设计了 25 个问题。Dreaming 从 2 轮扩展到 128 轮时，单独使用 Wiki 作答，评分覆盖从 13% 升到 48%。Wiki 与搜索一起用，整体得分从 54% 升到 61%；只用搜索是 53%。组合方式还使每个问题大约节省 20,000 Token。

并购材料上的另一组对比更直接：超过一半的评分点要跨越多份文档，其中不少还要判断或计算。咨询 Wiki 是 87%，只搜索是 73%。

Wiki 的价值取决于任务类型：

  • 需要跨文档关联、综合判断或计算时，Wiki 可能有明显优势。
  • 只需要从单一文档提取信息时，直接搜索可能更简单。原文另一项法律简报任务里，多数评分点用关键词就能从单份文档找到，Wiki 没有明显收益。
  • 如果 Wiki 只是把原文重新复制一遍，甚至比原始资料更庞大，就没有实现真正的抽象。有一个案例里，10 份文档约 115 KB，构建出的 Wiki 约 203 KB，是原始语料的 1.77 倍。

记忆表示的目标是降低未来理解和检索成本，而不是制造另一份更大的资料库。

第三个作用：把重要记忆提升到会话上下文

有些信息非常重要，Agent 不应该每次都等到任务开始后再搜索。Dreaming 可以把这类信息提升到记忆层级顶部，由 Agent Harness 在新会话开始时自动注入上下文。

但注入不是越多越好：

  1. 每条注入记忆都会消耗上下文 Token。
  2. 错误信息可能在每次会话中重复影响模型。
  3. 更长的指令文件不一定带来更好的遵循效果。

Anthropic 提到，Claude Code 的 Auto Memory 不会把所有记忆文件都加载进每次会话，而是只加载 MEMORY.md 的前 200 行或 25 KB（以先达到的限制为准）。这个文件相当于一个索引，告诉 Claude 已经记住了什么，以及需要时去哪里查找更详细的内容。

这一设计体现了上下文工程中的一个重要原则：

高频、稳定、关键的信息适合预加载；低频、细节化的信息适合按需检索。

Managed Agents 的 Dreams 还多了一道边界：一次 dream 读取已有 memory store 和 1 到 100 份 session，写出一份新的 store。输入不被修改，输出可以审完再挂上，也可以丢掉。

第四个作用：围绕目标塑造记忆

记忆并不一定要服务于所有可能的未来任务。不同 Agent 的职责不同，值得记住的信息也不同。例如：

  • 编程 Agent 更需要保存项目约束、代码结构、构建命令和已验证的调试经验。
  • 企业知识助手更需要保存业务概念、组织关系、流程规则和来源依据。
  • 个人助手更需要保存用户稳定偏好、长期目标和已确认的个人背景。

合同审查把“目标没写清”的后果量了出来。多个 Agent 同时往同一份合同条款汇总页写，发生相互覆盖。57 项评估事实只留下 41 项，覆盖率约 72%。随后构建指令改成：每份合同由单独 Agent 负责自己的页面，并尽量逐字引用合同条款，而不是把所有条款压进一个共享表格。调整后 57 项事实全部保留。

这组实验说明，记忆系统的质量不仅取决于模型能力，也取决于：

  • 记忆构建目标是否明确；
  • 哪些信息必须完整保留；
  • 多 Agent 并行写入时如何避免覆盖；
  • 对关键事实应当摘要，还是保留原文证据。

对法律条款、合规要求、接口规范等高精度信息，过度摘要可能造成不可接受的信息损失。

第五个作用：补齐跨会话留下的知识缺口

单次 Session 里的 Agent 只能看到当前任务范围内的信息，很难保证整个知识结构始终完整。构建 Wiki 时可能先写了页面链接，对应页面却还没创建；不同 Session 也可能用不同名称指向同一个主题。

Dreaming 可以跨多个 Session 检查这些结构性问题：

  • 查找指向不存在页面的链接；
  • 将错误链接重新指向正确页面；
  • 补充缺失的索引和主题页面；
  • 合并重复内容；
  • 检查页面之间的关系是否一致。

原文有一个案例：第二轮 Dreaming 找到 9 条指向不存在页面的链接，将其修正到已有页面，并新增 3 个页面，包括索引页。长期记忆的维护不只是内容维护，也包括知识结构本身的维护。

工程闭环

Anthropic 的实验可以归纳为一个工程闭环：

  1. 记录经验：保留 Session Transcript，确保重要结论有来源可查。
  2. 提炼记忆：从任务中筛选稳定、有复用价值的信息，而不是保存全部过程。
  3. 验证记忆：将记忆与原始记录、工具反馈或外部事实核对。
  4. 组织知识：在跨主题、跨文档任务确有收益时，构建 Wiki 等结构化表示。
  5. 选择性注入：将少量高价值信息放入启动上下文，其他内容按需检索。
  6. 持续维护：修复错误、过期内容、重复页面和断裂链接。
  7. 目标驱动：根据 Agent 的职责决定什么值得记住。

三个要先权衡的架构问题

1. 在线写入还是离线整理？

在线写入能够及时保存信息，但会占用 Agent 的注意力和任务 Token；离线整理对主任务干扰较小，却不能保证整理结果立即可用。

实际系统可以采用混合方式：在线阶段只记录高价值事件和必要线索，离线阶段再做系统性整理。

2. 如何保证记忆不过期、不失真？

记忆可能从一开始就错，也可能因为软件版本、项目状态、组织流程变化而失效。

因此，记忆最好携带来源、时间、验证状态和适用范围。对高风险事实，不能只依赖模型曾经写入的摘要，应当保留原始证据或可重新验证的路径。

3. 什么时候值得构建 Wiki？

Wiki 有维护成本，也可能变成另一套庞大、过时的知识库。

如果任务主要是单文档查找，搜索可能足够；如果任务经常需要跨文档关联、理解复杂实体关系或复用长期经验，结构化记忆才更有价值。

Dreaming 同样需要额外计算资源。没有必要无差别地频繁整理所有记忆，可以优先处理经常被访问、容易变化或曾经发生冲突的信息。

Anthropic 也把整理频率、优先级和验证范围留成开放问题。模型无法准确预知未来任务需要什么，这些选择仍要按具体应用评估。
